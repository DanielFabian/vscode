# Sovereign Patch-Stack Discipline

This repository is maintained as a small Sovereign patch stack on top of upstream VS Code. It is **not** a normal long-lived feature branch where every source edit goes directly on `sovereign/main`.

The short version:

- `sovereign/main` is the **recipe branch**: orchestration, workflows, scripts, docs, `sovereign/series`, and `sovereign/upstream-base` live here.
- `topic/<name>` branches are the **patch files**: source/product changes that should appear in the built editor live here.
- `topic-base/<name>` branches are the **patch delimiters**: `topic-base/<name>..topic/<name>` is the patch range that compose applies.
- `sovereign/integration` and `sovereign/develop` are **computed refs**: never commit to them and never treat them as source of truth.

If you are an AI agent, pause before every edit and classify it:

| Change kind | Where it belongs |
| --- | --- |
| Workflow, release script, compose script, docs about this fork | `sovereign/main` |
| `product.json`, `src/**`, `build/**`, `extensions/**`, or any change that must exist in the composed build | A `topic/<name>` branch |
| Adding/removing/reordering active patches | `sovereign/series` on `sovereign/main` |
| Advancing the upstream base | `sovereign/upstream-base` on `sovereign/main`, plus topic repair as needed |

The easiest mistake is to patch source on `sovereign/main` and assume CI will build it. CI does not. CI first composes `.git/sovereign-compose` from upstream base plus the topic ranges in `sovereign/series`, then builds that composed worktree.

## Branch roles

### `sovereign/main`

`sovereign/main` describes how to build Sovereign. It should contain:

- `.github/workflows/sovereign-*.yml`
- `sovereign/scripts/*`
- `sovereign/series`
- `sovereign/upstream-base`
- documentation and process notes

Do not put source/product patches here when the build output depends on them. A source change on `sovereign/main` is just recipe metadata unless a topic also carries that change.

### `topic/<name>`

A `topic/<name>` branch is one semantic patch. Keep it narrow enough that it can be reasoned about and repaired independently.

Rules:

- Keep topics linear; no merge commits.
- Prefer one coherent concern per topic.
- Source changes that should ship must be committed here.
- Topic commits may be rewritten while the patch is being repaired, but use `--force-with-lease` and coordinate with anyone else touching the topic.

Examples of current topics:

- `topic/product-quality-update-url`
- `topic/linux-archive-auto-update`

### `topic-base/<name>`

`topic-base/<name>` marks the start of the patch range. Compose applies:

```text
topic-base/<name>..topic/<name>
```

as cherry-picks onto the selected upstream base.

Move a topic base only when intentionally rewriting that topic after a successful repair. Do not casually delete or recreate topic bases; they are part of the patch-stack address space.

### `topic-repair-base/<name>`

When compose fails, `sovereign/scripts/compose.sh` writes a repair ref:

```text
topic-repair-base/<name>
```

at the freshly composed prefix before the failing topic. Rebase or recreate the failing topic on top of that repair base, validate compose, then update `topic-base/<name>` as part of the successful repair.

Repair refs are temporary; CI deletes stale ones after a successful canary.

### `sovereign/integration` and `sovereign/develop`

These refs are generated by compose:

- `sovereign/integration`: active topics listed in `sovereign/series`
- `sovereign/develop`: integration plus extra local `topic/*` branches when using `--develop`

Never check these out as working branches. Never commit to them. If you need to inspect or build the composed tree, use `.git/sovereign-compose` after running compose.

## Adding a new source patch

Use this shape for a new patch that should affect the built editor:

```bash
# Start from the current upstream base, a repair base, or another deliberate base.
base="$(awk 'NF && $1 !~ /^#/ { print $1; exit }' sovereign/upstream-base)"
git fetch origin 'refs/heads/topic/*:refs/heads/topic/*' 'refs/heads/topic-base/*:refs/heads/topic-base/*'
git fetch https://github.com/microsoft/vscode.git "refs/tags/$base:refs/tags/$base"

git branch topic-base/my-change "$base"
git switch -c topic/my-change topic-base/my-change

# Edit source/product files here.
git commit -m "area: describe the patch"

# Publish the patch refs.
git push origin topic-base/my-change topic/my-change
```

Then activate it by editing `sovereign/series` on `sovereign/main`:

```text
topic/my-change
```

and validate:

```bash
sovereign/scripts/compose.sh --base "$(awk 'NF && $1 !~ /^#/ { print $1; exit }' sovereign/upstream-base)"
```

If the topic depends on an earlier topic, list it later in `sovereign/series`. The order is semantically real.

## Editing an existing source patch

Do not edit the source file on `sovereign/main`. Work in the owning topic:

```bash
git worktree add /tmp/topic-product topic/product-quality-update-url
cd /tmp/topic-product

# Edit source/product files.
git commit -m "product: refine gallery behavior"
git push origin topic/product-quality-update-url
```

Then compose from the recipe branch and verify the generated worktree contains the change:

```bash
cd /path/to/vscode
sovereign/scripts/compose.sh --base "$(awk 'NF && $1 !~ /^#/ { print $1; exit }' sovereign/upstream-base)"
grep -R "expected text" .git/sovereign-compose/path/to/file
```

This check catches the common split-brain failure where workflow env or docs changed on `sovereign/main`, but the code needed by the build never entered the composed topic stack.

## Editing the recipe

Use `sovereign/main` for changes to the recipe itself:

- CI workflows
- compose/canary/release scripts
- docs
- `sovereign/series`
- `sovereign/upstream-base`

Examples:

```bash
git switch sovereign/main
$EDITOR .github/workflows/sovereign-build.yml
git commit -m "sovereign: refine build workflow"
git push origin sovereign/main
```

If a recipe change needs matching source behavior, split it deliberately:

1. source behavior goes in `topic/<name>`;
2. workflow/env/series behavior goes in `sovereign/main`;
3. local compose proves the two halves meet in `.git/sovereign-compose`.

## Validation checklist

Before pushing a contribution, run the checks that match the touched layer.

For source/product topic changes:

```bash
sovereign/scripts/compose.sh --base "$(awk 'NF && $1 !~ /^#/ { print $1; exit }' sovereign/upstream-base)"
```

Then validate the composed worktree, not just the recipe branch. For TypeScript under `src/`, follow the repository TypeScript validation rules. For TypeScript under `build/`, run:

```bash
cd .git/sovereign-compose/build
npm run typecheck
```

provided the composed worktree has dependencies installed or linked appropriately.

For workflow changes:

```bash
python3 - <<'PY'
from pathlib import Path
import yaml
yaml.safe_load(Path('.github/workflows/sovereign-build.yml').read_text())
PY
actionlint .github/workflows/sovereign-build.yml
```

For docs-only changes, at minimum run:

```bash
git diff --check
```

## Red flags for humans and AIs

Stop and reconsider if you are about to do any of these:

- commit a shipping source/product change directly to `sovereign/main`;
- commit to `sovereign/integration` or `sovereign/develop`;
- create a merge commit inside `topic/*`;
- move a `topic-base/*` ref without understanding the patch range it defines;
- assume CI builds the recipe branch without composing topics;
- add public service URLs to source/workflows when the point of the patch is to keep runtime product metadata behind a proxy;
- delete `topic-repair-base/*` before the repair has been incorporated.

If unsure, ask: "Is this recipe, or is this a patch?" That one question prevents most of the weird failures.
